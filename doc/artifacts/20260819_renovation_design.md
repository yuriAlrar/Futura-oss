# モバイル対応・円建て統一・グループ/セグメント機能 設計ドキュメント

## 0. 位置づけ

本ドキュメントは2026-08-19に実施した改修要件のヒアリング・現状調査・設計方針協議の結果をまとめたものです。`doc/specs/`配下の正式仕様書は実装完了後に本ドキュメントの内容を反映して更新する想定です。本書時点では未レビュー（作成者ドラフト）です。

## 1. 背景・要件サマリー

現状、ユーザーはほぼスマートフォン、管理者はPCで利用している。以下の要件に対応する。

1. BTC表記を全廃し円表記に統一（ダッシュボード・入出金リクエスト）。内部の相場レート機構はスキーマ上維持
2. 入出金リクエストのメモが消えることがあるバグの対応（**本改修では対応保留**、総合テスト時に再確認）
3. 取引履歴が直近20件までしか見えない制限を撤廃
4. ショートカットアイコン（ホーム画面追加時のアイコン/名称）を"Futura"表記から変更
5. ユーザーグループ（呼称：セグメント）の導入。顧客ごとに運用指標（+5%/+10%等）でグルーピングし、資産一括操作の対象を絞り込めるようにする
6. サブアカウント作成機能（本アカウントに紐づく複数アカウント運用への対応）
7. 招待コード制の新規登録ページ
8. アカウント停止（ログイン不可）とは別の「運用停止」状態の導入

## 2. 用語定義

| 用語 | 意味 | 管理方式 |
|---|---|---|
| グループ | 権限（RBAC）に関するグルーピング。administrator/user等 | AWS Cognitoグループ＋Permissionsテーブル（既存踏襲、変更なし） |
| セグメント | 運用指標（+5%運用など）に関する顧客グルーピング。1ユーザーが複数セグメントに所属可 | DynamoDBのみで管理。Cognitoは使用しない |
| 運用停止 | 一括資産調整の対象から除外するための、ユーザー単位のON/OFFステート | `User.operation_status`フィールド（セグメントではない） |
| 本アカウント | サブアカウントの作成元となる、通常のユーザーアカウント | 既存の`users`テーブル |
| サブアカウント | 本アカウント保有者が追加で作成する、別Cognitoユーザーとして発行されるアカウント | `users`テーブルに`parent_user_id`で紐付け |
| 招待コード | 新規登録ページでアカウント作成に必要な、使い切りのコード/リンク | 新規`invites`テーブル |

## 3. 要件別 決定事項

### 3.1 BTC表記の廃止・円統一

- **BTCレート概念は実質廃止**：1BTC = 1JPY固定とし、レートの変更操作はできないようにする
- スキーマ・内部フィールド名（`btc_jpy_rate`、`btc_amount`、`formatBTC`等）は将来の仕様変更に備えてそのまま温存する。変更するのは**画面上の表示文言のみ**（"BTC"という単語をフロントエンドのUIテキストから除去し、円表記に統一）
- 相場レート管理画面（[admin/rates.vue](../../pages/admin/rates.vue)等）は画面自体は残すが、作成・更新などの編集操作はdisabled/エラーとする
- ユーザー向け相場推移グラフ（[BTCRateChart.vue](../../components/user/BTCRateChart.vue)）はレートが動かなくなるため撤去する
- 入出金リクエストの金額確定は「リクエスト時点のレートでBTC量を確定し、承認時は再計算しない」方式のまま維持する（レート固定化により実質的にリスクは消えるが、将来のレート復活に備えてリクエスト時のJPY換算額をスナップショット保存する）

### 3.2 メモ消失バグ

- コードレビューの範囲では明確な原因を特定できなかった（GSIのprojectionはALL、承認処理も`memo`をスプレッドで保持しており消失箇所が見当たらない）
- **本改修では対応を保留**。総合テストのタイミングで再現手順を確認してから改めて対応する

### 3.3 取引履歴の全件表示

- バックエンドAPI（[transactions/index.get.ts](../../server/api/transactions/index.get.ts)）は既にpage/limitパラメータを受け付ける設計。制限の主因はフロント側UIのデフォルト件数
- フロントエンドにページネーション/無限スクロールUIを追加する
- [transaction-requests.get.ts](../../server/api/transaction-requests.get.ts)の`status='all'`時の全件scanは将来的なパフォーマンス懸念があるため、可能であれば複数GSIクエリのUnion方式に見直す（優先度は低）

### 3.4 ショートカットアイコン

- `/public`ディレクトリ自体が存在せず、`favicon.ico`実体なし。`apple-touch-icon`・Webアプリマニフェストも未整備なため、ホーム画面追加時にOSがページタイトル文字列（"Futura"）をそのまま表示している
- favicon・apple-touch-icon・manifest.jsonを新規作成する
- `nuxt.config.ts`（title: 'Futura'）と[app.vue](../../app.vue)（title: 'M・S CFD App'）でタイトルが二重管理・矛盾しているため統一する
- **未決**：最終的な正式名称・アイコン素材は未確定（要デザイン素材・名称決定）

### 3.5 セグメント（運用グループ）

- セグメントは**対象絞り込み専用**。所属しても自動的に率が適用されるわけではない。一括操作（batch-operations）実行時に「どのセグメントに対して操作するか」を選ぶUIを用意し、率は従来通り管理者が都度入力する
- Cognitoグループとは独立させ、DynamoDBのみで管理する（詳細はデータモデル参照）

### 3.6 運用停止ステート

- セグメントの一種としてではなく、`User`に専用フィールド（`operation_status: 'active' | 'suspended'`）を追加する形で表現する
- 制限範囲は**一括操作（batch-operations）の対象からの除外のみ**。ログイン可否・個別の入出金リクエスト・管理者による個別取引作成には影響しない

### 3.7 サブアカウント

- ログイン中のユーザーが、自分のセッションから新規サブアカウントを作成できる機能とする。**招待コードは不要**（認証済みであること自体が本人確認の代替になる）
- ただし、作成されたサブアカウントも**管理者による承認は引き続き必要**（`profile_approved: false`で作成し、既存の承認フローに乗せる）
- パスワードは仮パスワード発行 → サブアカウント自身が初回ログイン時に変更（既存の管理者作成ユーザーと同じUXフロー、[change-initial-password.post.ts](../../server/api/auth/change-initial-password.post.ts)を流用）
- メールアドレスは実在の別メールアドレスが必須（Cognito標準のusername=email制約をそのまま使用）
- `users`テーブルに`parent_user_id`を追加し、逆引きGSIで本アカウント⇔サブアカウントを紐付ける

### 3.8 招待制登録

- サーバー側で`AdminCreateUser` + `AdminSetUserPassword`を使う方式を採用（**Cognitoインフラ変更不要**）。招待コード検証後、サーバーが管理者権限でCognitoユーザーを作成し、ユーザーが入力したパスワードをその場で本パスワードとして確定させる
- Cognitoのセルフサインアップ（`SignUp`API + PreSignUp Lambda）は不採用（Lambdaトリガー新設等インフラ変更が重いため）
- 新規`invites`テーブルが必要。招待リンクの発行・一覧・失効を行う管理画面が新規に必要
- 未認証で叩ける公開エンドポイントになるため、レート制限・入力バリデーションを必須要件とする
- 登録直後のユーザーは`profile_approved: false`とし、既存の承認フローに乗せる

## 4. データモデル変更

### 4.1 `users`テーブル拡張

| 追加フィールド | 型 | 説明 |
|---|---|---|
| `parent_user_id` | String（任意） | サブアカウントの場合、本アカウントの`user_id`。本アカウント自身は未設定 |
| `operation_status` | String（`active`\|`suspended`） | 運用停止ステート。デフォルト`active` |

追加GSI：`ParentUserIndex`（hash: `parent_user_id`）— 本アカウントから見たサブアカウント一覧取得用

### 4.2 新規テーブル：`segments`（マスタ）

| フィールド | 型 | 説明 |
|---|---|---|
| `segment_id` | String（PK） | セグメント識別子 |
| `name` | String | セグメント名（例：+5%運用セグメント） |
| `description` | String | 説明 |
| `created_by` / `created_at` / `updated_at` | String | 監査用 |

### 4.3 新規テーブル：`user_segments`（多対多紐付け、隣接リストパターン）

| フィールド | 型 | 説明 |
|---|---|---|
| `PK` | String | `SEGMENT#{segment_id}` |
| `SK` | String | `USER#{user_id}` |
| `joined_at` | String | 所属開始日時 |

GSI：`UserSegmentIndex`（hash: `SK`相当の`user_id`側、range: `segment_id`側）— ユーザーを起点に所属セグメント一覧をGSI一発で取得

これにより要件の「グループ（セグメント）をキーに所属ユーザーをGSI一発」「ユーザーをキーに所属セグメントをGSI一発」の双方が実現できる。

### 4.4 新規テーブル：`invites`

| フィールド | 型 | 説明 |
|---|---|---|
| `invite_code` | String（PK） | 招待コード（推測困難なランダム文字列） |
| `status` | String（`active`\|`consumed`\|`revoked`） | 状態 |
| `created_by` | String | 発行した管理者 |
| `created_at` | String | 発行日時 |
| `consumed_by` | String（任意） | 使用したuser_id |
| `consumed_at` | String（任意） | 使用日時 |

### 4.5 `transactions`テーブル拡張（非キー属性、Terraform変更不要）

| 追加フィールド | 型 | 説明 |
|---|---|---|
| `requested_jpy_amount` | Number（任意） | リクエスト時点のJPY換算額スナップショット |

### 4.6 `batch_operations`テーブル拡張（非キー属性、Terraform変更不要）

| 追加フィールド | 型 | 説明 |
|---|---|---|
| `target_segment_id` | String（任意） | 対象を絞り込んだセグメントID |

### 4.7 `market_rates`テーブル

スキーマ変更なし。1BTC=1JPYの固定レコードをシードし、以後の作成・更新APIをアプリケーション側でブロックする。

## 5. 権限（Permission）追加

| キー | 説明 | 付与対象 |
|---|---|---|
| `segment:create` / `read` / `update` / `delete` | セグメント管理 | 管理者 |
| `account:create-sub` | サブアカウント作成 | 一般ユーザー（デフォルト権限に追加） |

## 6. インフラ（Terraform）変更範囲

- `infra/dynamodb/main.tf`：`users`テーブルへの属性・GSI追加、`segments`/`user_segments`/`invites`テーブル新設
- `infra/cognito/`：**変更なし**（招待制登録を方式A＝AdminCreateUser方式で実装するため）
